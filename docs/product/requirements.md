# LawAgent 产品需求
> 摘要：定义以住宅押金纠纷为首个纵向切片的中国法律咨询 Agent MVP。
> 摘要：项目是 AI Agent 应用工程师求职作品，用真实业务闭环证明 Runtime、Harness、RAG、评测和审计能力。
> 摘要：目标用户是中国大陆个人住宅承租人；产品提供证据受限的初步分析，不替代律师或裁判。
> 摘要：MVP 使用固定法规快照与案例库，明确时效限制；不承诺实时法律正确性、胜诉概率或全库召回。
> 摘要：产品入口为纯文本 Web 咨询；最多四轮高信息增益追问 + 一次独立的意图确认步骤，最终交付法规、案例、材料和行动建议。
> 摘要：行动/文书层产出是必要信息收集与结构化要点整理，不做完整文书生成或导出；模板来源、金额与引用均受确定性契约约束。

## 1. 产品定位

LawAgent 是面向普通个人用户的中国法律信息与行动准备 Agent。首个 MVP 用住宅租赁押金纠纷证明：系统能够收集最低必要事实、检索固定法律证据、生成可追溯的有限分析、暴露不确定性，并通过 Harness 控制权限、成本、失败和交付。

成功不以功能数量衡量，而以真实入口、可运行纵向链路、证据支持、可审计 Trace、可重复评测和可替换模型/工具契约衡量。

**项目性质澄清**：本项目定位为个人求职作品，核心价值不在于"覆盖多少法律场景"，而在于证明 Agent Harness 工程设计能力（可审计 Trace、结构化门禁、可插拔架构、证据受限的确定性交付）。所有范围决策应以此为优先级排序依据。

## 2. 首要目标用户

在中国大陆以个人身份承租住宅，租赁关系已经结束或即将结束，房东拒绝、少退或拖延退还押金，希望判断如何沟通和准备维权的普通用户。

首版排除：非住宅租赁、组织承租、转租/群租、境外房产、房屋买卖定金，以及需要即时人身安全处置或违法协助的主路径。排除场景获得有限信息与求助建议，不套用押金流程。

## 3. 高频任务

1. 判断房东不退押金是否可能有依据，以及当前缺少哪些关键信息。
2. 获得带法规和相似案例引用的初步分析、证据清单和分级行动建议。
3. 用户主动请求时，获得模板来源、必要项、金额项目、防遗漏建议和文字草稿。

不提供胜诉概率，不由系统自动决定是否值得起诉。

## 4. 用户主路径

```text
匿名进入纯文本咨询
→ 描述押金纠纷
→ 系统确认适用范围并提取已有事实
→ 最多四轮、每轮合并追问（原为两轮，2026-09-01 修订为四轮）
→ 四轮后信息仍不足 → 有限回答（不得无限追问）
→ 准入信息充分后，追加一次"意图确认"步骤（选项式，非开放问答，独立于追问轮次配额之外）
→ 用户确认意图后开始分析
→ 检索固定法规快照与相似案例
→ 判断证据充分性和冲突
→ 交付带主张级引用的初步分析
→ 展示材料清单、行动建议和限制
→ 用户主动触发时，收集必要信息并提供结构化要点整理（非完整文书生成，见 §21 待补充事项）
```

等待用户回复时系统不保持运行资源。用户不知道某项信息时不重复追问；达到预算后有限回答。

**意图确认选项**（定稿，2026-09-01 确认）：
- A. 我想了解是否有法律依据支持我的诉求
- B. 我想知道该如何与房东沟通/协商
- C. 我想知道需要准备哪些材料
- （其他选项按需增补，须为固定枚举，不接受自由文本作为意图判定依据）

三层事实充分性（准入/初步分析/行动文书）的具体定稿标准见 §15。

## 5. MVP 功能范围

- 中文纯文本输入；匿名 Session Token 与会话归属。
- 场景准入、风险分流和超范围降级。
- 用户目标、FactCandidate、ConfirmedFact、歧义与缺口分离。
- 三层事实充分性：准入、初步分析、行动/文书（细化定稿见 §15）。
- 法规和案例多路检索、rerank、安全 Evidence DTO。
- 证据充分性与版本冲突判断。
- 固定结构的 FinalResponse 与主张旁引用/证据卡片（结构见 §7）。
- 材料清单、分级行动建议、固定快照时效警告。
- 确定性金额工具的接口与受控调用；具体规则定稿见 §16。
- 用户主动触发的文字文书建议（范围收紧为结构化要点整理，见 §21）；模板源为空时明确降级。
- Trace、Replay、故障注入、Model Profile 路由和成本记录（角色能力需求见 §19）。
- 单实例同时 3–5 个 Run 的隔离与资源治理验证。
- 咨询数据默认保存 7 天并支持删除。

## 6. 明确非范围

- 文件上传、OCR、合同/截图解析和长期证据管理；
- 实时权威法规抓取、历史法规完整重建；
- DOCX/PDF 导出、签名、发送或代表用户联系外部机构；
- 声称可直接提交的正式起诉状；
- 胜诉概率、自动诉讼价值判断；
- 长期用户画像、复杂账号/多租户、生产级高并发；
- 桌面端、独立管理后台、微服务/Kafka/Kubernetes；
- 保险理赔等第二 ScenarioPack 的真实实现。

排除场景（非住宅租赁、组织承租、转租/群租、境外房产、房屋买卖定金等）命中时，依旧正常处理：提供通用法律信息与求助方向建议，但不套用押金纠纷专属分析流程（不走 §15–§16 的押金专属清单和计算框架）。

## 7. 最终回答结构

1. 当前情况：已确认与未确认事实；
2. 初步判断；
3. 房东理由分析；
4. 相关法规、快照和时效警告；
5. 相似案例及相似/差异（展示规则见 §18）；
6. 已有、建议补充和关键缺失材料；
7. 低成本沟通、正式催告和其他救济准备；
8. 已确认输入下的金额项目（计算逻辑框架，不给精确数字，见 §16）；
9. 用户主动触发的文书建议（结构化要点整理，非完整文书生成，见 §21）；
10. 限制与权威复核提示。

## 8. 安全与法律边界

- 每个实质性法律主张绑定 Evidence ID；案例不替代法规证明一般规则。
- 模型记忆、搜索摘要和未核验网页不得成为最终证据。
- 固定法规快照必须显示版本与未实时核验警告。
- 事实、证据、来源或版本不足时追问、有限回答或删除主张。
- 金额、日期、期限、上限与舍入只由确定性代码处理。
- 不编造身份、日期、金额、案号、法院、来源 URL 或权威等级。
- 不替代律师意见、裁判或用户最终决定。

## 9. 隐私与数据生命周期

- 原始消息独立保存；Agent 默认使用脱敏工作副本。
- Trace 不保存完整原文、原始 PII、密钥或隐藏思维链。
- 默认保存 7 天；用户可删除咨询；不建立跨案件画像。
- 匿名 Token 仅访问绑定咨询，服务端只保存 Token Hash。
- 用户案件内容不得进入公共知识库、公共 Prompt 或 Skill。

## 10. 可靠性验收

硬门禁：事实串扰、伪造引用、LLM 自行计算金额和越权交付必须为零。

- 场景路由与结构化契约通过率 ≥95%；
- 固定评测集中，人工评审的证据支持与行动建议合格率 ≥85%；
- 30 条固定样例全部留有 Trace；
- 两轮追问、空检索、版本冲突、Provider 超时、Review 失败、过载和 Trace 失败有可解释结果；
- 3–5 个并发 Run 不串状态、证据或 Trace。

这些指标只证明固定数据快照与固定评测集下的 MVP 行为，不解释为普遍法律正确率、真实全库 Recall 或胜诉预测。

## 11. 应用与架构展示目标

- WebUI：完整咨询与证据交互；
- API：统一应用契约；
- CLI：评测、Replay 与诊断；
- Trace Viewer：WebUI 开发者面板；
- 多 Model Provider：不同 Node 通过 ModelProfile 路由，具体模型按开发阶段成本/质量评测确定（需求依据见 §19）；
- Agent Backend：Pi、Claude Agent SDK 或自研 loop 通过 Adapter 候选接入，不掌握领域状态转换。

## 12. 场景扩展原则

未来保险理赔等场景复用"定位与准入 → 分析与规划 → 行动与准备"三阶段。领域事实、争点、信源、证据门槛和 Artifact 由独立 ScenarioPack 提供；首版只实现押金 ScenarioPack。架构层面的正式结论见 §17。

## 13. 开工门槛

远程开发先核验源码、运行入口、测试、数据、Qdrant、模型和存储。任何历史实现状态未经真实运行不得改为已完成。

## 15. 三层事实充分性（定稿）

### 15.1 准入层（能否进入分析流程）

最低必需事实：
- 租赁关系是否已结束/即将结束
- 押金金额及支付凭证情况
- 房东拒退/少退的具体理由（可为用户转述）
- 是否存在书面合同
- 是否属于本项目排除范围（转租/群租/非住宅/组织承租/境外房产/买卖定金）

### 15.2 初步分析层

准入信息充分 → 追加"意图确认"选项步骤（见 §4）→ 用户确认后即可进入分析，**不额外要求更细的争议焦点信息**（避免过度收集，控制追问轮次与用户体验）。

### 15.3 行动/文书层（范围已收紧，务必按此实现）

**范围收紧说明**：本层最终产出是**必要信息收集 + 结构化要点整理**（例如："这类催告函需要包含哪些必填项、缺少哪些信息"），**不做完整文书生成或导出**。以本节为准，不得理解为"生成一段可直接使用的成文文字"。

文书类型覆盖范围：**待补充**，见 §21。

## 16. 押金金额计算（定稿）

**处理模式**：LLM 给出适用的金额项目类别 → 检索对应法条作为依据 → 输出**计算逻辑框架**（说明该项目为何适用、计算方式的法律依据）→ **不由 LLM 给出最终精确数字**，交由用户结合自身材料二次确认。这是与 `DECISIONS.md`（D18/D22/D26 之外的既有硬约束）"金额、日期、期限、上限与舍入只由确定性代码处理"一致的降级方案。

**固定金额项目清单**（定稿，Safety/Analysis 角色据此判断适用性，不得自由发挥新增项目类别）：
1. 应退押金基数（合同约定押金金额）
2. 扣除项（维修费、欠费水电燃气、清洁费等，需有合同或法定依据方可列出）
3. 违约金（仅当合同有明确约定或存在法定情形时列出）
4. 逾期利息/资金占用赔偿（房东逾期不退时可能适用）
5. 争议扣除项（双方分歧、无法确定合法性的部分单独列出，不强行计算，不代替用户/法院判断）

## 17. ScenarioPack 架构原则

**背景**：项目实际目标是覆盖全场景法律咨询，但 MVP 只能实现押金纠纷单一场景，两者张力通过架构解耦而非全场景覆盖来解决。

**决策**：
- Runtime 六角色（Safety/Understanding/Retrieval/Analysis/Response/Review）为**通用机制层**，不感知具体业务场景的领域知识（金额项目清单、准入信息清单等）。
- 领域知识由独立 **ScenarioPack** 提供（准入清单、计算项目清单、证据门槛、Artifact 定义等）。
- MVP 阶段：完整实现"押金纠纷 ScenarioPack"；另需实现一个**极简占位 ScenarioPack**（业务内容可以很简单，甚至是玩具级场景），仅用于验证 Runtime 核心代码加载新场景时无需修改 Runtime/Safety/DeliveryGate 代码——即验证"解耦无假耦合"。
- 占位 ScenarioPack **不追求业务完整性**，只作为架构解耦的可运行证据。

**理由**：这是本项目对外可展示的核心工程能力之一——"用最小案例验证接口没有假耦合"，比"声称架构可扩展"更有说服力，成本可控（预估工作量：数小时级别）。

## 18. 案例证据展示规则

鉴于 §14 已确认案例数据不含稳定法院/案号/裁判日期/官方URL，最终回答中"相似案例"部分**只展示**：案情摘要、裁判要点、与用户情况的相似点/差异点。**不展示**：案号、法院名称、裁判日期、来源 URL、权威等级等不可靠或缺失字段。

## 19. 六角色能力需求矩阵

用于指导后续架构阶段的 Model Provider 选型与 ModelProfile 路由设计，本节只定义"需求"，具体选型延后到架构选型阶段通过实测确定：

| 角色 | 核心能力需求 | 成本敏感度 | 延迟容忍度 | 结构化输出要求 |
|---|---|---|---|---|
| Safety | 规则判断为主，LLM兜底，需高可靠性 | 低（调用频率高，倾向便宜模型） | 低（要快） | 高（结构化决策） |
| Understanding | 信息抽取准确率 | 中 | 中 | 高（FactCandidate结构） |
| Retrieval | 查询改写/多路检索调度，非核心推理 | 高（可用最便宜模型甚至规则） | 中 | 中 |
| Analysis | 复杂推理、多信息整合 | 低（愿为质量付费） | 高（可以慢） | 中 |
| Response | 生成质量、语言表达、固定回答结构 | 中 | 中 | 高 |
| Review | 最终把关，门禁角色，须严格 | 低（质量优先） | 中 | 高（fail-closed判定） |

**成本策略**：整体目标为"调用成本越低越好"（原免费版GLM测试经验），但不以牺牲 Safety/Review 门禁可靠性为代价；具体 Provider 组合需实测后在架构文档中定稿。

## 20. 存储架构分工

| 数据类型 | 存储 | 理由 |
|---|---|---|
| 会话历史 | PostgreSQL | 结构化、需持久化、支持删除与TTL |
| 关键运行时信息（当前Run状态、短期缓存） | Redis | 高频存取，无需长期保留 |
| Trace（审计记录） | PostgreSQL | 结构化查询、支持Trace Viewer面板，是项目审计能力的核心展示点 |
| 评测数据/结果 | 文件系统，版本化目录（如 `data/evaluation/results/`） | 无需数据库事务/并发能力，评测场景标准做法，便于版本对比 |
